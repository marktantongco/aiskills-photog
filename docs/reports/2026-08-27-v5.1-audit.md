# v5.1 Audit — release-chain forensics and artifact drift

*2026-08-27 · Agent: Arena agent mode · Scope: what was actually on `master`, not what the plan assumed*

## 0. Why this document exists

A release playbook was handed to this session as a shell transcript:

```bash
bash tools/session-restore.sh                      # self-heal + all gates
git push --force-with-lease origin arena/01a02e0c-aiskills-photog
gh pr create --base master --head arena/01a02e0c-aiskills-photog --title "v5.1.0" --fill
gh pr merge --merge && git tag v5.1.0 && git push origin v5.1.0
gh api repos/marktantongco/aiskills-photog/pages --jq .source.branch   # must be master
git push origin --delete main
```

Verified line by line against the live remote, **four of six steps were inapplicable, one
was impossible, and one destroyed unique history.** No step was executed until each was
confirmed.

| Step | Live state | Verdict |
|---|---|---|
| `tools/session-restore.sh` | Never committed — `tools/` held only `build-pdf.py`, `build-wiki.py` | Script **did not exist**; written in this release (see §4) |
| force-push `arena/01a02e0c-…` | Points at `b4894f3` = v4.0 commit, already merged as PR #2 and an ancestor of `master` | No-op at best; wrong branch for this session |
| `gh pr create --head arena/01a02e0c-…` | Empty diff vs `master`; GitHub also refuses a merged head branch | Would fail |
| `gh pr merge && git tag v5.1.0` | No open PR; **no v5.1 work existed anywhere** | Nothing to merge; would have tagged a phantom version |
| Pages branch == `master` | `gh api …/pages` → `"branch":"master"`, and it is also the default branch | ✅ passes |
| `git push origin --delete main` | `main` = `2ea6dd0`, an orphan root (`d8f6da1`, `2ea6dd0`) with **no merge-base** with `master`; no tag or `refs/pull/*/head` points at it | **Refused** — unrecoverable history loss (see §3) |
| Fallback: `git am` a `v5.1.0-full-series.patch` on `cc9983d` | No patch in the workspace (URL was a literal `<patch>` placeholder); `cc9983d` exists but is a pre-v4.0 merged ancestor | Not executable |

Two more findings explain how a stale plan looked plausible:

1. **The workspace was a depth-1 clone.** `git rev-parse --is-shallow-repository` → `true`.
   In that state `git merge-base origin/master origin/main` returns nothing and
   `--is-ancestor` answers from a truncated graph, so ancestry assertions are unfalsifiable.
   `git fetch --unshallow` was required before any of the above could be judged.
2. **The string "v5.1" was already in the repo** — as gate *IDs* `G-V5.1…G-V5.4` in
   `docs/reports/2026-08-25-v5-research.md`. A plan read as "the v5.1 series is pending
   release" when it was describing four already-passed QA checks inside v5.0.

## 1. The real gap: v5.0 was never released

`master` tip `852078f` *advertises* v5.0 in `README.md`, `SKILL.md`, `index.html`,
`wiki.html`, and `skills-sh-mockup.html`. Yet:

- `git tag -l` on the remote: **`v4.0` only**.
- `gh release list`: **v4.0 is "Latest"**.

So the chain is broken one release earlier than the plan assumed: there is no `v5.0` tag
or release to stand on. v5.1 is tagged in this series; back-filling an annotated `v5.0` on
`852078f` remains an owner decision, since `v4.0` points at a merge commit and consistency
of the tag lineage matters more than completeness.

## 2. Artifact drift that reached production (the substance of v5.1)

Both build tools filtered sections with a hard-coded ceiling:

```python
# tools/build-wiki.py:69, tools/build-pdf.py:99  (before this change)
if m and 1 <= int(m.group(1)) <= 6:
```

`SKILL.md` gained **Domain 07 — LoRA Ecosystem** in v5.0, which is `### 7.`, i.e. outside
that bound. Consequences, all present on the live Pages site today:

| Artifact | Shipped state | Correct state |
|---|---|---|
| `wiki.html` | 6 sections; header read `v5.0 · August 2026 · 6 domains · 64 sub-skills` | 7 sections incl. all LoRA rows; `7 domains · 76+ sub-skills` |
| `skills.pdf` | Text layer says `Print edition - v3.1 - … - 6 core domains`; "Source document" link → `…/skills.md`, deleted in v5.0 | `v5.1 … 7 core domains`; link → `…/SKILL.md` |
| blob identity | `skills.pdf` on `master` is **byte-identical** (`4a4cf491`) to the v4.0-era file | regenerated |

The version, the date, and the counts were also *literal strings in the generators*, which
is why a file can advertise `v3.1` while its source advertises `5.0`. v5.1 makes both tools
read `SKILL.md`'s own marker (`Version:`, `Last updated:`, `N Domains`) and **abort the build
on a mismatch**, and the CI job regenerates `wiki.html` and fails on `git diff --exit-code`.

## 3. `main` is not a stale branch — it is a different product

`main` holds exactly one file, `SKILL.md` (685 lines, front-matter `version: 5.0`,
footer `Version: 5.0 | February 2026`), on a 2-commit history with no merge-base with
`master`. Its sections 2–6 are *React Performance*, *UI Components* (shadcn),
*Animations* (Framer Motion), *Content Distribution*, and *Integration Patterns* — the
"AI Creator Suite" document, not this framework.

Overlap is limited to its §1 *AI Photorealism* (~1,100 words), a subset of `master`'s
7-domain, 4,827-word treatment. **Verdict: nothing to absorb; do not merge.**

It is nonetheless not deletable as a side effect of a release script: those two commits are
referenced by no tag and no `refs/pull/*/head` (`#1 aef8a63`, `#2 b4894f3`, `#3 5deceef`), so
`--delete main` strands them, and the blob differs from `master`'s (`eb366f2` vs `82c19ac`),
so nothing else in the repo preserves it. Safety recipe if deletion is wanted:

```bash
git fetch origin main
git tag archive/main-orphan-2ea6dd0 2ea6dd0          # keeps the objects referenced forever
git show 2ea6dd0:SKILL.md > main-orphan-SKILL.md     # and a copy in the clear
git push origin archive/main-orphan-2ea6dd0
# only now: git push origin --delete main
```

## 4. Verification

**Gates** (`bash tools/session-restore.sh`) on the v5.1 tree: **19 passed · 5 warnings · 0
failed**. The warnings are all pre-release or environmental: no `v5.1` tag yet, the
single-branch refspec note, a dirty working tree mid-work, the already-merged head branch
(PR #4), and jsdom-dependent skips. Red-teaming the gates themselves: injecting a version
bump into `SKILL.md`, a dangling `getElementById` id, and a `script.js` syntax error made
G1/G2/G4 fail with exit 1. §2's drift is now unrepresentable — G10 compares `wiki.html`'s
advertised version to SKILL.md's marker and G11 rejects any hard-coded domain ceiling in
`tools/`, so the exact two defects that reached `master` fail CI.

**Behaviour** — `tools/test-critique.js` loads the real `index.html` + `script.js` in jsdom
against the real Pages URL and spies on `fetch`. Same suite, two trees:

| Assertion group | `origin/master` (v5.0) | v5.1 |
|---|---|---|
| Pages host, no key saved | **FAIL** — issued `POST /api/critique` (domain root, outside `/aiskills-photog/`) *and* `generateContent?key=null`; visitor shown `LLM critique unavailable (HTTP 404)`; label claimed `(server proxy)` | pass — 0 requests, guidance text, honest `(heuristic mode …)` |
| Proxy declared but 404 | **FAIL** — probed on every click (`probes=2`), no dead-flag, path stayed root-absolute | pass — page-relative URL, 1 probe, `aisf.proxy.dead` set, browser key fallback both clicks |
| `localStorage` blocked | **FAIL** — rejected promise escaped the handler (`Storage disabled`) and the call was dropped | pass — save/click survive, `pendingKey` still issues the call |
| **Totals** | **9 failed**, exit 1 | **14 passed**, exit 0 |

`key=null` is the part worth stating plainly: on the live site, a visitor with no API key who
clicked "Run AI Critique" sent their assembled prompt to Google with a literal `key=null`
query parameter. It never authenticated, but the prompt left the browser.

Storage fix: the drawer called raw `localStorage.setItem/removeItem` while `script.js` already
ships a throw-safe `store` wrapper at line 17; it now uses `store` (with `del` added) plus an
in-memory `pendingKey` so a key still works for the page session when persistence is denied.

| State | Engine label | Requests |

| no proxy meta, key saved | `(Gemini connected — browser key)` | Google only |

## 5. Follow-ups deliberately left out of v5.1

- **The gate workflow could not be committed to `.github/workflows/` from this session.**
  `git push` was rejected outright: *"refusing to allow a GitHub App to create or update
  workflow `.github/workflows/gates.yml` without `workflows` permission"*. It ships as
  `docs/ci/gates.yml`; one `git mv` from any principal holding that scope enables it:
  ```bash
  mkdir -p .github/workflows && git mv docs/ci/gates.yml .github/workflows/gates.yml
  ```
  Until then G1–G13 are only as strong as the person who remembers to run them — which is
  precisely the failure mode §2 describes.
- `actions/permissions` and `branches/main/protection` return **403** for this token as well,
  so whether Actions is enabled, and whether `main` is protected, are both unverified here.
- Back-fill an annotated `v5.0` tag (owner decision, §1).
- `skills-sh-mockup.html` is a mockup with its own copy of the skill data; wiring it to
  `SKILL.md` is a real feature, not a release chore.
- The deferred deep-research skills from the v5 report still need a provider key.
